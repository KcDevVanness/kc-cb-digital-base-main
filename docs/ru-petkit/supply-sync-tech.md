### 0.2 通用查询参数（游标：背景、需求、解法）

#### 背景：快照会变，日期查不到“变了什么”

贵方数据来自定时脚本汇总的快照文件（2 小时到每天 2 次），同一业务日期内会发生多次变更：价格调了（reprice 一天可调多次）、订单状态流转了（15 个状态）、单证补了（`docs_complete` 从 false 变 true）、成本手工改了。只按业务日期查（`date_from/date_to`）只能回答“某天的数据是什么”，回答不了“自上次拉取后什么变了”——同一天内的三次变更只看到最后一次，快照重跑覆盖了某天也不知道要重拉，漏拉一天就是一个洞，要人工对 `total` 才发现。

#### 需求：每天只拉变更行，漏了能续上

我方每天拉一次，需要：① 只拿上次之后变更的行（数据量小）；② 同一天内多次变更不丢；③ 某页拉失败下次能从断点重拉，不丢不重；④ 和按日期查配合使用（日期定窗口，游标做增量），不是二选一。

#### 解法：`updated_since` 增量游标（三步走）

语义：**只返回 `updated_at` 严格大于 `updated_since` 的行**（大于，不含等于，避免边界漏行）。每行自带 `updated_at`（行级更新时间），我方存下见过的最大值作 CUR。

```text
第 1 次（全量）：GET /api/v1/supply/stock?page=1&page_size=100
  → 存下响应里最大的 updated_at，记为 CUR = "2026-09-27T10:00:00+03:00"
第 2 次（增量）：GET /api/v1/supply/stock?updated_since=2026-09-27T10:00:00%2B03:00&page=1
  → 只拿 CUR 之后变更的行；翻完所有页后 CUR 更新为新的最大值
第 3 天及以后：重复第 2 步。失败页不更新 CUR，下次重拉同一游标。
```

| 参数 EN | 类型 | 必填 | 说明 CN | 说明 RU |
|---|---|---|---|---|
| page | integer，从 1 起，默认 1 | 否 | 页码，分页 | номер страницы |
| page_size | integer，1 到 500，默认 100 | 否 | 每页条数，分页 | размер страницы, пагинация |
| updated_since | string，日期时间（RFC 3339，例 `2026-09-27T00:00:00+03:00`，加号需编码为 `%2B`） | 否 | 增量游标，见上三步；不传就是全量第一页 | курсор, без параметра — полная выборка |

三条硬规则：同一游标翻页时保持 `updated_since` 不变、`page` 递增；先翻完所有页再更新 CUR（`total` 对不上就告警）；`updated_at` 缺失的行视为全量，我方告警并按全量处理，不静默丢。

#### 和按日期查的关系（一句话）

`date_from/date_to` 定窗口（要哪段），`updated_since` 做增量（这段里什么变了）。首次全量不用游标，之后每天只用游标翻页。游标是严格大于（不含等于），要求 `updated_at` 单调递增——见 22 验收第 3 条冒烟集。

#### 我方使用方式（作用、怎么用、落到哪）

作用：游标是我方同步作业的断点续传依据。没有它，每天全量 17 个逻辑端点既慢又容易洞；有了它，每端点每天只拉变更行，失败页重拉同一游标即可，不丢不重。

```text
定时作业（每天 1 次，每端点独立 CUR）：
  1. 读本地游标表（tenant + endpoint → CUR，无记录即全量）
  2. 带 CUR 翻页拉取，逐页 upsert 投影表（自然键去重，重放安全）
  3. 全页成功 → CUR 更新为本批最大 updated_at（cursor-after-success）
  4. 任一页失败 → CUR 不动，告警，下次同一游标重拉
```

落点（待建表，名待 PRD 定稿，当前代码无此表）：CUR 存游标表（tenant + endpoint 唯一）；投影行存快照表（endpoint + 自然键 + as_of 唯一）。下游只读投影：驾驶舱读最新快照，PO 草稿读 plan 投影，对账读 settlements 投影——都不直调贵方接口。游标断超 24 小时，驾驶舱整页标 stale，禁按旧数下决策。

| `date-time` | string，RFC 3339 | `"2026-09-27T18:15:58+03:00"` | 时间；游标 `updated_since` 与 `updated_at` 用此格式 |

| `enum` | string，取值见各端点枚举表 | `"in_transit"` | 一律英文码，无俄文字段（详见 0.5）。 |
| `currency` | string，ISO 4217 三字母大写 | `"RUB"` / `"USD"` | **每个金额 / 价格对象自带**，不靠端点隐含（库存 ₽、发运 $ 混用） |

### 0.5 英文硬约束（返回结构只用英文）

**硬约束：所有返回 JSON 的 key、枚举码、状态值、单位、类型关键字一律英文；不得出现任何俄文字段名、俄文枚举值、俄文单位。**

旧 `_label` 机制取消：凡之前写 `<field>` + `<field>_label`（俄文）成对出现的一律改为**只保留英文 `<field>`**，`_label` 字段不再返回、不再解析。俄文只存在于本规范的“说明 RU”栏（给人核对页原文用），绝不进入线上 payload。

例：`"status": "in_transit"`（合法）；`"status": "в пути"` / `"status": "в пути"`（非法，我方拒绝入库）。
`name` 等品名原文例外：值内容可为俄文（商品名本身），但 key 必须英文。

### 0.6 金额对象

```json
{ "amount": "57658.00", "currency": "RUB" }
```

**金额硬规则（全 17 个逻辑端点统一，RU→我方方向）：金额 2 位、单价 4 位，HALF_UP 四舍五入（half-away-from-zero，与我方 `trade_docs/lib/money.ts`（`AMOUNT_SCALE=2`、`PRICE_SCALE=4`）同语义）。⛔ 违反即拒收，无例外。** 金额例 `1.005 → "1.01"`（整数补零 `74 → "74.00"`，负数对称）；单价例 `"341.2382"` 原样保留 4 位。**全链路只有一次舍入**：行金额 = `HALF_UP(数量 × 单价, 2)`，合计 = 已舍入行金额的精确求和，不做二次舍入（合同样本：`700 × 341.2382 = 238866.74` 恰好；`180 × 65.5916 = 11806.488 → "11806.49"`）。RU 为外部集成：金额非 2 位、单价超 4 位 → 显式 HALF_UP 量化到 2/4 位并记结构化 warning 后入库，不静默截断；人工录入超标 → 400 拒绝。内部不做多币种金额位差异化（含 JPY 一律 2 位）。
**贵方禁止事项（MUST NOT）：** ① 禁止用 JSON number 传金额/单价（必须十进制字符串，否则二进制浮点吃掉分位）；② 禁止 `Number.toFixed` 舍入（`1.005` 会变成 `"1.00"`，少一分钱）；③ 禁止单价压到 2 位（`341.2382 → 341.24` 会让首行金额变成 `238868.00`，与合同差 1.26）；④ 禁止合计二次舍入（合计只能精确求和已舍入的行金额）；⑤ 禁止静默截断超标位数（必须量化记 warning 或 400）。违反任一条 → 我方拒绝入库并告警，联调不通过。

| 参数 EN | 类型 | 必填 | 说明 CN | 说明 RU |
|---|---|---|---|---|
| amount | `decimal` | 必填 | 金额，十进制字符串 记账与验算 | сумма, decimal, учёт |
| currency | `currency` | 必填 | 币种 区分 ₽ / $两边混用，不可省略 | валюта, обязательна |

```json
{ "price": "341.2382", "currency": "CNY" }
```

**价格对象**（单价专用，4 位）：`price` 为单价十进制字符串（合同 `Unit Price` 列口径，如 `"341.2382"`、`"65.5916"`、`"1188.2500"`）；`currency` 同金额对象。单价录入后不再舍入，票面按 4 位打印；凡 `unit_price` / `price` / `price_discounted` / `buyer_price` / `payout_price` / `showcase_price` / `cost` / `unit_cost`（`Себестоимость` 为单件成本时）一律用价格对象。金额对象只装行小计、合计、费用、毛利（2 位）。
