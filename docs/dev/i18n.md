# 多语言（i18n）

## 适用范围

本仓当前**只服务 en 与 zh**。平台基线是 `en | pl | es | de | ko`，`zh` 不在基线里，
所以「加 zh」和「去掉 pl/es/de/ko」是两件不同的事，分别需要不同的扩展点。

## 一句话结构

```
src/lib/i18n/app-locales.ts            本部署服务哪些语言（唯一 owner）
src/types/i18n.d.ts                    让 zh 在类型层成为合法 Locale（declare module）
src/lib/i18n/register-dictionary-loader.ts
                                      注册 zh + 语言 → 字典的解析
src/lib/i18n/served-locales.ts         请求期收窄：layout 用 filter，路由处理器用 resolver 槽
```

## 三个收窄入口（缺一不可）

只删字典是**不够**的：`loadDictionary` 对找不到的语言会回落到默认语言，
所以 `locale=de` 的 cookie 会渲染出一个英文页面，但语言切换器里仍然列着德语。

| 入口 | 作用对象 | 实现 |
|---|---|---|
| `resolveServedLocales()` | 根 layout、backend layout → `detectLocale` / `I18nProvider` / 切换器 | 把 `resolveSupportedLocalesForRequest()` 的结果过滤到 `appLocales` |
| `registerServedLocalesResolver()` | 不走 layout 的调用方：`POST /api/auth/locale` 等路由处理器 | 占住框架唯一的 supported-locales resolver 槽 |
| `loadAppDictionary()` 的 `default` 分支 | 显式解析到未服务语言时 | 返回英文。平台只对「非基线语言」自动垫默认语言，`pl/es/de/ko` 是基线，不垫，会渲染出裸 key |

### 为什么要占 resolver 槽

`getSupportedLocales()` = 基线 ∪ 已注册，框架**没有减法接口**；唯一的收窄口是
`translations.supported_locales`（**按租户**），而它的默认值是全基线——一个从未保存过
选择的租户会把德语放回来。产品级的「永不出德语」只能用 resolver 槽表达。

槽的语义是「这个租户 opt-in 了哪些语言」，所以占了槽就必须继续回答这个问题：
`served-locales.ts` 在 `src/modules.ts` 启用了 `translations` 时会把租户选择与本部署语言求交集，
没启用时直接返回本部署语言。**开启 `translations` 不需要再改代码。**

注册位置在 `src/di.ts` 的 `register()`——那是唯一「在所有模块 DI registrar 之后」的钩子；
`translations` 模块在模块作用域填这个槽，注册早了会被它覆盖。layout 侧的 filter 独立兜住
注册完成前的窗口。

## 一条字符串只用一种语言（硬规则）

**任何给人看的字符串都不许中英并列**，「供应商货号 Supplier code」「深圳盐田 Yantian」
「采购合同 / PURCHASE CONTRACT」都属于同一类缺陷：中文读者读到噪音，英文读者读到中文，
而语言切换器两边都修不好。分三类各自落地：

| 表面 | 规则 | 约束者 |
|---|---|---|
| 界面文案（组件、页面、flash、错误提示） | 一律走 `t('key', 'English fallback')`；key 在模块 `i18n/{en,zh}.json` 里各写各的语言，**兜底写英文** | `scripts/i18n-check-hardcoded.mjs`（硬编码）＋ `src/lib/i18n/__tests__/language-purity.test.ts`（混排） |
| 字典 / 主数据 label（`setup.ts` 播种、字典库维护） | 数据**没有**语言维度（`dictionaries:dictionary_entry` 的 `label` 只有开了 `translations` 才可按语言翻译），所以一条只写一种语言，且**只写显示名**；记录真正存的机器码由**选择器**渲染成 `CODE — 名称`（`PCS — 件`、`FEEDING — 喂食`、`USD — 美元`），不往 label 里粘 | 同上（seed 检查） |
| 打印/导出文档（合同 XLSX、CSV 表头） | 标题走 `t()`，由**生成时的语言**决定：合同用 `resolveTranslations()`，CSV 表头用路由里静态配置（工厂的 `header` 没有语言入口 → 该文件的语言只能是英文，不能混排） | 合同：`lib/contractTemplate.ts`；CSV：路由的 `export.columns` |

允许保留的「西文」只有三类，都不算第二种语言：**品牌/产品/协议名**（Ozon、TikTok Shop、
Meilisearch、OpenAI…）、**缩写**（SKU、MOQ、HS、PDF、L/C）、**机器码与占位符**
（`{count}`、`products.items.view`、`supplier_product_unit`、`40HQ`）。例外清单在
`language-purity.test.ts` 的 `LATIN_NAME_ALLOWLIST` / `LATIN_PHRASE_ALLOWLIST` 里，
新增一条要写清理由。

**播种里的 `name` / `description` 也算文案**：它们是字典库页面上给人看的元数据，同样一种语言。
字典条目要展示机器码时，改的是**读取侧的 loader**（`products/lib/unitOptions.ts`、
`sourcing/components/quoteSectionOptions.ts`、`purchasing/components/orderFormOptions.ts`），
不是往 label 里塞代码。

自查（两条都在门禁里）：

```bash
yarn test src/lib/i18n/__tests__/language-purity.test.ts   # 字典与 seed label 的混排
yarn i18n:check-hardcoded                                  # 组件里没走 t() 的硬编码英文（advisory）
```

改完字典要跑 `yarn generate`（分片按语言文件切）；`src/i18n/` 下的 app 字典不需要。

**已有环境**：字典/种子的 label 是数据，播种是 insert-only，所以规则改变**不会**自动改写已经写库的旧 label。
在 `/backend/config/dictionaries` 改一次即可，或走同一路径的 API（本次是把旧的双语 label 用
`PATCH /api/dictionaries/<dictionaryId>/entries/<entryId>` 同步到新写法）。

## 字典放哪

| 文件 | 内容 | 谁合并它 |
|---|---|---|
| `src/i18n/<locale>.json` | app 级字典（app 自有文案、`ui.*`、`api.*`、`startPage.*`…） | `registerAppDictionaryLoader` |
| `src/modules/<id>/i18n/<locale>.json` | 模块字典。包内已有同名语言时，app 的会 **spread 覆盖上去** | `yarn generate` 生成的分片 |
| `node_modules/@open-mercato/*/i18n/<locale>.json` | 框架包自带（**没有 zh**） | 同上 |

`zh` 的加载顺序：英文基底（平台为「非基线语言」自动垫）→ app 级 `zh.json` → 各模块的 `zh.json`。
所以漏翻一个 key 会掉到英文，不会渲染出裸 key。

因为框架包不带 zh，**每个启用的核心模块都要有一份 app 覆盖层**才算翻完：当前 17 个官方模块
（`auth`/`directory`/`configs`/`entities`/`query_index`/`audit_logs`/`notifications`/`dashboards`/
`attachments`/`search` + `catalog`/`customers`/`sales`/`wms`/`currencies`/`dictionaries`/
`feature_toggles`）各有覆盖层，`api_docs`/`events`/`integrations`/`data_sync` 没有；app 自有模块
各自带 `i18n/{zh,en}.json`。覆盖层与包内 `en.json` 逐键对齐。

自查（只数「仅含 `i18n/` 的官方覆盖层」目录，应输出 17）：

```bash
for d in src/modules/*/; do [ -d "$d/i18n" ] && [ "$(ls -A "$d" | wc -l)" = "1" ] && basename "$d"; done | wc -l
```

## 常用操作

### 改/加一个文案

1. 在 `src/i18n/en.json` 加 key（或对应模块的 `en.json`）
2. 在 `src/i18n/zh.json` 加同名 key——**两个文件的 key 集合必须一致**
3. 不需要 `yarn generate`（`src/i18n/` 下的 app 字典不经过生成器）
4. 组件里用 `t('your.key', 'English fallback')`，不要写死字符串

### 加一个语言（例如 `ja`）

1. `src/types/i18n.d.ts` 里 `LocaleRegistry` 加 `ja: true`
2. `src/lib/i18n/app-locales.ts` 的 `appLocales` 加 `'ja'`
3. `src/lib/i18n/register-dictionary-loader.ts` 的 `registerLocales([...])` 加 `'ja'`，
   并加一个 `case 'ja'` 指向字典文件
4. 建 `src/i18n/ja.json`，以及每个启用模块的 `src/modules/<id>/i18n/ja.json`
   （建议先复制 `en.json` 保证 key 齐全，再逐条翻）
5. `yarn generate` —— 生成器按**磁盘上存在的语言文件**切分片，不跑就没有 `ja` 分片

### 启用租户级收窄

在 `src/modules.ts` 加 `{ id: 'translations', from: '@open-mercato/core' }`，
跑 `yarn generate` 和迁移。之后 `Settings → Module Configs → Translations` 的选择
会在 `appLocales` 范围内生效，`served-locales.ts` 无需改动。

## 验证方式

下面的端口以 dev 日志 `Local:` 行里实际打印的为准（本机 `APP_URL` 是
`http://localhost:3100`，见 [setup.md](./setup.md) 的端口说明）。

```bash
# 只接受 en/zh，其余 400
for l in de pl es ko zh en; do
  curl -s -X POST http://localhost:3100/api/auth/locale \
    -H 'content-type: application/json' -d "{\"locale\":\"$l\"}" -w " HTTP %{http_code}\n"
done

# cookie 决定渲染语言；de 应落到 en
curl -s -H 'cookie: locale=de' http://localhost:3100/start | grep -o '<html lang="[a-z-]*"'
curl -s -H 'cookie: locale=zh' http://localhost:3100/start | grep -o '<html lang="[a-z-]*"'

# key 集合一致
node -e "const a=require('./src/i18n/en.json'),b=require('./src/i18n/zh.json');\
const m=Object.keys(a).filter(k=>!(k in b));console.log('zh missing:',m.length)"
```

页面侧还要看一眼语言切换器**只列两个**选项（框架自带的 endonym 表对 `zh` 走
`Intl.DisplayNames` → `中文`，不需要额外配）。
