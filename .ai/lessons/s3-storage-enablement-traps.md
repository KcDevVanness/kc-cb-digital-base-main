# Enabling the S3 provider is a three-way contract: the flag at build, the flag at runtime, and a scope-carrying driver config

**Context**: Phase 0 of [`.ai/specs/2026-09-23-local-to-s3-storage-migration.md`](../specs/2026-09-23-local-to-s3-storage-migration.md) installed and wired `@open-mercato/storage-s3@0.8.0` while both attachment partitions kept `storage_driver='local'`, then probed the provider through the app's own seam (`StorageDriverFactory`) against a local S3 endpoint. Four traps surfaced that no single file states.

**Problem**:

1. **The enable flag lives in two different places at two different times.** `src/modules.ts` registers `storage_s3` behind `OM_ENABLE_STORAGE_S3`, and `yarn generate` / `yarn build` bake the resulting module list into `.mercato/generated/**` — so module *loading* is decided at generate/build time. The partition settings page (`/backend/config/attachments`) instead reads the **request-time** `process.env`. Observed on a production build started without the variable: `s3Enabled=false` in the page's RSC payload while `GET /api/storage-providers/s3/list` already answered `401` (route registered) — the two halves disagreed. The reverse combination is the dangerous one: UI offers S3 while no `s3` driver is registered, and `StorageDriverFactory.resolveForAttachment` then falls back to the **local** driver for the unknown key (`@open-mercato/core/.../drivers/driverFactory.ts:69`), so an `s3` partition would read and write local disk with S3-shaped paths. Production images carry no `.env` (`docs/deploy/runtime.md`), so the flag must be injected by the deployment environment at build *and* run time. The dev side has the same trap in miniature: a long-running `yarn dev` keeps the environment it booted with — editing `.env` restarts the Next child but not the supervisor that injected it, so an env-gated UI keeps rendering the old value until the whole supervisor restarts (observed: `touch .env` restarted Next, `s3Enabled` stayed `false`). Verify env-dependent UI on a process that started after the edit.
2. **The driver's tenant-scope assertions are inert without a scope in the config.** `S3StorageDriver` takes `this.scope` from `config.organizationId`/`tenantId`. Probed with a hand-built config: a key with no `org_*`/`tenant_*` segments was **accepted**; the same key against a driver whose config carried the scope was rejected (`[internal] S3 key is not scoped to the active tenant`). Only the module's credential enhancer, reached through `resolveForPartition(partitionCode, scope)`, injects the scope — so any tool that builds an S3 driver by hand silently loses the isolation check. The partition assertion (`… is not scoped to the requested partition`) is scope-independent and fires either way.
3. **The repo's rehearsal endpoint no longer runs.** `localstack/localstack:latest` now exits 55 with "License activation failed — no credentials were found" unless a paid `LOCALSTACK_AUTH_TOKEN` is set. MinIO replaced it in all three compose files: image `quay.io/minio/minio` (the `minio/minio` Docker Hub repo is gone), MinIO's default in-container addresses (9000 API / 9001 console) published as `MINIO_PORT`/`MINIO_CONSOLE_PORT` on the host, healthcheck `["CMD","mc","ready","local"]` (the image ships `mc`, and its built-in `local` alias points at the container's own 9000 — a custom `--address` breaks that healthcheck), and `forcePathStyle` is mandatory on the client side. Self-hosted/MinIO endpoints are also rejected by the provider's SSRF guard unless `OM_STORAGE_S3_ALLOW_INTERNAL_ENDPOINTS=true`.
4. **`store()` of an existing key throws.** The provider writes with `IfNoneMatch: '*'`, so a re-store answers `PreconditionFailed` rather than overwriting — a resumable copy must read the object back (length, then hash for a sample) before deciding to skip it, never blindly re-store.
5. **A run needs one driver per scope, not one per run (2026-09-23, `storage_ops` Phase 1).** `verify` resolved a single `s3` driver from the first row's scope; the second tenant's object then came back "missing or unreadable", because the driver's `assertKeyAddressable` rejects a key outside its own tenant. A partition's rows can belong to different tenants/organizations, and the credential enhancer is scope-aware, so the correct unit is one memoized driver per `(tenantId, organizationId)` — `copy`, `verify`, `rollback` and `prune-local` all share that resolver now.
6. **A CLI child regenerates the discovery registries from *its own* environment (2026-09-23).** A spec-spawned `yarn mercato storage_ops …` child whose environment lacked `OM_ENABLE_STORAGE_S3` regenerated `.mercato/generated/**` **without** `storage_s3` — the driver then vanished for every later run in that tree and `migrate` failed with `the "s3" driver is not registered (resolved "local")`. The registry regeneration is a side effect of bootstrap, so "the flag at runtime" also covers every process that shells the CLI (spec runners, deploy hooks, cron). The integration specs therefore declare `OM_ENABLE_STORAGE_S3` in `__integration__/meta.ts`, and the refusal message names the fix.

**Rule**: treat S3 enablement as a contract across three surfaces, and verify all three before trusting a partition flip.

- Keep `OM_ENABLE_STORAGE_S3` identical at generate/build time and at runtime; inject it in the deployment environment (production has no `.env`). A mismatch in the "runtime true, build false" direction is a silent local fallback, not a visible error.
- Resolve S3 drivers only through `resolveForPartition(partitionCode, scope)` with the row's own `(tenantId, organizationId)`; never assemble a driver config by hand, or tenant isolation is unenforced. Assert the resolved driver's `key` equals the partition's configured driver before doing anything with it.
- In a multi-tenant tool, cache drivers **per scope** — one driver per run rejects every other tenant's key.
- Any process that shells the mercato CLI (spec runner, deploy hook, cron) must carry the same flag environment as the runtime: bootstrap regenerates the discovery registries from the child's environment.
- Rehearse against MinIO (compose profile `storage-s3`), not LocalStack; open internal endpoints explicitly.
- When copying objects, read back before re-storing; a `PreconditionFailed` means "already there", and the manifest — not the header — owns the skip decision.

**Applies to**: `src/modules.ts` (the `storage_s3` registration), any `storage_ops`-style operator tool, the attachments partition settings page, `docs/deploy/storage.md`, deployment pipelines that build and run this app, and every future provider whose enable flag gates both a generated registry and a runtime UI read.
