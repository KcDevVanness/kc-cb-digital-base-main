## TLDR

Give the supplier product library a **rule-driven code generator** instead of free-typed codes: business
staff maintain the brand and category code lists in the existing 字典库 page, a new app-owned
`product_codes` module owns the code rules (segments, separator, serial width and scope) and the
**issuance ledger** that makes a code unique and never-reused, and the supplier product form gets a
**生成** button whose result is rendered as a **breakdown** (`PK-CL001` → 品牌 PK（PetKit）· 类别 CL（猫砂）· 序列 001).
The same rule definitions are read **backwards**, so any code already in the system — including the
irregular PetKit-era codes and hand-typed ones — is explained best-effort instead of being rejected.
Legacy PetKit codes are **never renumbered**: the ledger is the only proof of "machine-issued", so a row
that is not in it is a legacy code by definition, and no backfill is required.

## Problem Statement

**Codes are typed by hand today, so the library has no regular identity.** `purchasing_supplier_products.supplier_sku`
is a required free-text field (`data/validators.ts:198`, `components/SupplierProductForm.tsx:576-585`) with only
length and per-supplier uniqueness; on promotion it is written verbatim into `products_products.sku`
(`lib/supplierProductPromotion.ts:227`). Whatever the operator types becomes the product master's identity.

**The house rule exists but lives in a spreadsheet.** The user-supplied `Super pawers 产品表.xlsx` (outside the
repo) documents two coexisting schemes — the 14-digit 成品项目编码 (`SP010201001RU` = 品牌+一级分类+二级分类+开发类型+流水号+国家) and the
产品SKU型号 (`SP-CL001`, `SP-CL001-4`) — plus the brand table (SP / DK), the category letters in actual use
(CL 猫砂 / TP 尿片 / LB 猫砂盆 / LS 猫砂铲 / CB 餐具) and the per-row 项目编号 column. None of it is enforced
anywhere in the app, and the workbook itself is inconsistent (duplicate `SP-SL017`/`SP-SL018`, LS/SL mixed for
猫砂铲, a shared barcode across three SKUs, one column-offset row) — so it cannot be imported as truth either.

**Nothing tells an operator what a code means.** The library list renders `itemNo ?? supplierSku`
(`components/SupplierProductsTable.tsx:98`) and the product form renders the SKU as an opaque string. A
reader cannot tell brand from category from serial, which is exactly why codes drift.

**The PetKit-era codes are live and irregular.** Legacy SKUs are PetKit item numbers (`P4108`, `P4108-UVC`,
`P9906`, `PD10`, `PKCL11`, `P41171-5PCS`, `PKCL10-4BAGS` — `sourcing/lib/skuDerivation.ts` header) with no
brand/category/serial structure, and they are already frozen into document snapshots
(`trade_docs_contract_lines.sku`, `trade_docs_invoice_lines.sku`, `purchasing_purchase_order_lines.product_snapshot`,
`cross_border_shipment_allocations.product_snapshot`). They must keep working while new brands (SP, and the
next ones) follow a rule.

**A compatibility trap sits in the write path.** `productUpdateSchema = productCreateSchema.partial()`
(`products/data/validators.ts:248`) re-validates `sku` against `^[A-Za-z0-9._\-/]{1,64}$` (`:57,208`) on every
update, and the product form always submits `sku` (required field, `components/ProductForm.tsx:1133-1137`). A
legacy code that violates that charset cannot be edited at all — not even its name.

**And a rename lands on two same-sounding fields.** `供应商货号` (`supplier_sku`) and `原始货号` (`item_no`)
read as the same thing in Chinese, while the first is the library key *and* the future master SKU and the
second is the supplier's own printed number.

Affected users: the buyer maintaining the library, the operator reading a code on a document, and whoever
maintains brand/category vocabulary today by asking an administrator.

## Overview and Success Measures

- **Primary outcome:** a new supplier product row in the library receives a code produced by a maintained
  rule (`PK-CL001`-shaped) with its breakdown visible in the form, and every existing code in the system —
  PetKit legacy included — still saves, searches, promotes and prints exactly as before.
- **Leading indicators:** share of library rows whose code exists in the issuance ledger; number of rule
  edits per month (rules are maintained by business staff, not by a deployment); count of codes whose parse
  returns `none` (should fall only for new rows, never for legacy ones).
- **Baseline:** zero machine-issued codes; two dictionaries do not exist (`product_brand`, `product_category`);
  no rule entity, no ledger, no breakdown, no compatibility guard.
- **Market / product reference:** mid-market ERP item numbering — Odoo's sequence-backed `product.template.default_code`
  with configurable prefixes, SAP's number-range objects with external (manual) number assignment, NetSuite's
  auto-generated item names with a "legacy code" field. Adopted: **internal vs external numbering** (a code
  the system issues and a code the supplier prints, kept on separate fields), **number ranges that never
  recycle a number**, and **external/manual assignment left legal** for migrated data. Rejected: renumbering
  historical items (breaks printed documents), and validating legacy codes against the new rule (would make
  the old data uneditable).

## Goals

- **REQ-PC-001** — Brand and category code lists (`product_brand`, `product_category`) are seeded by the new
  module and maintained by business staff in the existing 字典库 page; an entry's **label** may change, its
  **value** may not change or be deleted once the issuance ledger holds a code for it.
- **REQ-PC-002** — A code rule is a first-class, organization-private, soft-deleted, optimistic-locked record:
  name, mode (`generate` | `carry_over`), ordered segments (dictionary-backed value segments + exactly one
  serial segment), separator, serial width, serial scope, `enforce` (`warn` | `strict`), active flag. Saving a
  rule rejects any rule whose worst-case output breaks `^[A-Za-z0-9._\-/]{1,64}$`.
- **REQ-PC-003** — Issuance is atomic and monotonic: the ledger's unique index is the guarantee, a losing
  concurrent insert retries with the next serial, and a number is **never** reused — including by a
  soft-deleted library row. A `dryRun` preview returns the next code without consuming it.
- **REQ-PC-004** — Every generated code is returned with a **breakdown**: one part per segment carrying the
  stored value and the dictionary label (`品牌 PK（PetKit）`), so the form, the list and the rule page can render
  the same explanation without a second query.
- **REQ-PC-005** — **Reverse parsing** explains any code that already exists, in three states — `issued`
  (found in the ledger), `full`/`partial` (matches a rule's shape; a segment value missing from its dictionary
  is shown as-is and marked 未登记), `none` (no rule shape matches → 「沿用旧码」). Parsing never errors and
  never writes.
- **REQ-PC-006** — The supplier master carries an optional **默认品牌** (`brand_value`, from `product_brand`)
  and the library row carries an overridable **品牌** that defaults from it; generation refuses to guess when
  neither is set.
- **REQ-PC-007** — The supplier product form offers **生成** beside 商品 SKU, shows the breakdown underneath,
  and **never blocks** a hand-typed code: the panel labels what it read (`规范编码` / `手工编码` /
  `沿用旧码`) and leaves the value editable. 生成 fills a starting value — the rule describes the shape of
  *one* brand's codes, so a brand it does not describe is typed by hand exactly as before (owner 2026-09-24:
  「品牌+类别的方式只是一个工具，方便生成输入编码」). `enforce` (`warn` | `strict`) is therefore a rule
  field with **no write-path effect yet** — no command reads it; the `strict` escalation to a rejection is
  deferred, not implemented. The one code-change action that *is* gated is 改用规范编码, which is disabled
  once the row is promoted (the master's SKU must not be re-cut behind printed documents). The rule used
  is resolved deterministically: an explicit `ruleId`, else the single active `generate` rule, else
  400 `rule_ambiguous` (several) / 404 `rule_not_found` (none) — `carry_over` rules are never used to generate.
- **REQ-PC-008** — Legacy codes are read-only by default: a code absent from the ledger displays as 「沿用旧码」,
  is never renumbered by any batch operation, and re-coding is an explicit, single-row action — refused once the
  row is promoted — that records the retired code as a `ProductCodeAlias`, which both the product list and the
  supplier library list then match when searching by code.
- **REQ-PC-009** — Grandfathering: `products.items.update` no longer re-validates an **unchanged** SKU against
  the charset pattern, so a product whose legacy SKU contains characters the pattern forbids can still be
  edited (name, spec, prices).
- **REQ-PC-010** — Promotion guard: when the master product for a row's code already exists **and another
  supplier product row points at it**, promotion refuses with a readable error naming 关联已有商品, instead of
  overwriting the other supplier's data.
- **REQ-PC-011** — The two code fields are renamed by ownership: `supplier_sku` → **商品 SKU** (ours, required,
  becomes the master SKU), `item_no` → **供应商货号** (the supplier's own, optional), across the form, the list,
  the search placeholder, the purchase-order detail label, both locale files and the module READMEs.

## Non-goals

- **The 14-digit 成品项目编码 rule** (`SP010201001RU`, dev-type and country segments) — the engine is
  data-driven, so this ships later as **rule configuration plus two dictionaries**, not as code. The numeric
  一级/二级分类 code lists and the `product_dev_type` list are not created here.
- **Product-master fields for 项目编码 / 开发类型 / 销售国家** — `products_products` gains nothing.
- **Batch renumbering of legacy codes**, and any migration that rewrites an existing `sku`.
- **A second code-list maintenance page** — the 字典库 page already owns this surface.
- **Supplier identity inside the code** — the prefix is the brand; a supplier's own `code` stays on the
  supplier record for reconciliation and documents.
- **Merging the four existing `prefix + padStart(4)` number generators** (`purchasing/commands/orders.ts:462`,
  `sourcing/commands/shared.ts:101`, `cross_border/commands/shipments.ts:172`, `trade_docs/commands/contracts.ts:255`)
  into one shared helper — the new ledger follows the same convention (the unique index is the real guarantee)
  but adds a bounded retry those call sites do not have, and does not refactor them.
- **The 生产批次号 and 物料编码 rules** from the workbook.

## Proposed Solution

A new app-owned module **`product_codes`** owns three things nothing else should: the **rule model** (what a
code is made of), the **issuance ledger** (which codes the system issued, and their serials), and the
**parser/explainer** (forward breakdown and backward reading share one implementation, so they cannot drift).
Code lists stay where this deployment already keeps them — the `dictionaries` module, whose page the app
already owns (`src/modules/dictionaries/backend/config/dictionaries/page.tsx`) and whose write scope is already
organization-aware — so business staff maintain them with `dictionaries.manage`, no new UI.

`purchasing` gains two nullable columns (supplier default brand, row brand) and calls the generator from the
form; it stores whatever code results, exactly as today. `products` gains one compatibility fix (grandfathering)
and one guard (do not overwrite a master another supplier row owns). The reverse parse is what makes the two
worlds coexist: legacy rows simply parse to `none` and are displayed as 沿用旧码.

### Design Decisions and Alternatives

| Decision | Rationale | Alternative considered | Why rejected / deferred |
|---|---|---|---|
| Ledger table is the source of truth for "machine-issued" | No backfill, no flag column, no migration on existing rows; a code either is in the ledger or it is not | `code_source` column on `purchasing_supplier_products`, backfilled as `legacy` | Requires a data migration over live rows and invents a value the system cannot verify |
| Issue the number when 生成 is clicked (not at save) | The code the operator sees is the code that gets stored; a save-time allocation would silently change the displayed value | Preview-only, allocate on save | The displayed code would not be the stored code; a 409 after typing the whole form is worse than a burned number |
| Burned numbers are accepted | A number that is issued but unsaved stays spent, which is what makes "never reused" true | Reclaim unsaved numbers | Reclaiming re-opens the concurrency hole the ledger closes; an occasional gap in a sequence is harmless |
| Prefix is the **brand**, not the supplier | A code is the product's identity; buying the same item from a second factory must not change it | Prefix from `purchasing_suppliers.code` | Re-keys a product on every sourcing change, and the supplier's own code is what we are moving away from |
| Parse is best-effort and never fails | Operators must be able to read a code they did not generate; a legacy code is data, not an error | Reject unparseable codes | Would make legacy rows uneditable, the same trap `REQ-PC-009` fixes |
| A segment can opt out of the separator (`join`) | The rule as written by the business is `SP` + `-` + `CL001`: the category letters and the serial form one token. Modelling it as "one separator between every pair" produced `SP-CL-001` — caught by the unit tests before any number was issued | A literal segment holding `-` | A literal is invisible to validation (it cannot reason about worst-case width) and makes the shape harder to read in the editor |
| Serial scope is brand + category | The workbook's project-code serials run continuously across 二级分类 (001–015), so a per-二级 scope contradicts the source data; brand+category keeps `PK-CL001` readable | Global serial; per-二级 serial | Global loses the category context; per-二级 contradicts the workbook |
| Code-list **values** are immutable once issued | A renamed value silently changes the meaning of every code that used it | Allow value edits | Would corrupt parse results with no trace |
| Grandfathering moves the charset check from the update schema into the update command's changed-value branch | Widening a validator is allowed (`BACKWARD_COMPATIBILITY.md` §Convention files / validators); narrowing is not | Exempt specific legacy SKUs by list | A list rots; the rule "validate what you change" is stable |

## Domain Vocabulary and Business Rules

Only the terms whose meaning is not already fixed by the Goals, the data models or the API contracts; everything
else is defined once, in those sections.

| Term / invariant | Precise meaning or rule | Source of truth | Failure behavior |
|---|---|---|---|
| 商品 SKU / 供应商货号 | Our code for the item (the library key, and the value written into `products_products.sku` on promotion) versus the code the supplier prints (optional, never used for matching) | `purchasing_supplier_products.supplier_sku` / `.item_no` | 409 `supplier_product_sku_taken` on a duplicate; a blank 供应商货号 is normal |
| 沿用旧码 / 手工码 | A code absent from the ledger: 沿用旧码 when no rule shape matches it, 手工码 when a shape matches but the system did not issue it | ledger absence + parse status | none — both are normal states, displayed, searchable, promotable |
| Value immutability | A `product_brand` / `product_category` entry whose value appears in the ledger cannot be re-valued or deleted | ledger | 409 `dictionary_value_in_use` |
| Never reuse | A serial is consumed at issuance and never returned, even if the row is later deleted or the issuance is never saved | ledger (append-only) | none — by construction |

Trusted scope is derived server-side exactly as the sibling modules do it: `ensureScope(ctx)` (the helper
`purchasing`'s own commands use, `purchasing/commands/shared.ts:33`) reads `tenantId` + `organizationId` from
the command context, never from the request body, and every ledger, rule and alias query filters on both. A missing scope fails closed. No

## Reuse and Ownership Map

| Capability | Reuse / extend / app-own | Existing module or new module | Integration seam | Why |
|---|---|---|---|---|
| Code lists (品牌/类别) | Reuse | installed `dictionaries` (+ the app's page override) | dictionary API + seeded entries | The deployment already keeps `supplier_product_unit`, `container_type`, `payment_terms` there; a second code-list UI would be a parallel convention |

| Library row brand + generate button + breakdown | Extend | app-owned `purchasing` | form field + one API call to `product_codes` | The form is the only place an operator types a code |

changed a product (the spec adds **no** second change log). Nothing here duplicates CRM, auth, notifications
or workflow capability.

## Architecture and Data Flow

```text
buyer (供应商产品表单)  -> POST /api/product_codes/generate  -> rule lookup (product_codes_rules)
                        -> ledger insert, unique-index retry (product_codes_ledger_entries)
                        -> { code, breakdown[] }
                        -> purchasing.supplier-products.create|update  -> purchasing_supplier_products
                        -> (later) purchasing.supplier-products.promote -> products.items.create|update

any reader             -> GET /api/product_codes/parse?code=…  -> ledger hit? -> issued
                                                               -> else rule shapes -> full|partial|none
                                                               -> { status, breakdown[], source }

re-code (explicit)     -> POST /api/product_codes/aliases     -> product_codes_aliases
                        -> products / supplier-products list search unions aliases
```

- **Module boundaries:** `product_codes` owns rules, issuance and parsing only; it holds no product data and
  no supplier data. It never writes into `purchasing` or `products` tables — the caller stores the code it
  returns. That keeps "who issues" and "who stores" separable and lets the same generator serve a future
  14-digit rule.
- **Extension points:** the code-list guard is a **command interceptor** on the installed
  `dictionaries.entries.create|update|delete` commands — the same seam `scope_guards` already uses for `auth`
  (`src/modules/scope_guards/commands/interceptors.ts`) — so the installed module stays untouched; the
  dictionary page keeps the app's existing override; no installed page is edited.
- **Alternatives considered:** a shared helper extracted from the four existing number generators (rejected as
  an unrelated refactor — see Non-goals); storing the breakdown on the row (rejected: it is derivable, and a
  stored copy would rot when a label changes); a `code_source` column (rejected in favour of ledger presence).
- **Compatibility:** `purchasing_supplier_products.supplier_sku` keeps its name, uniqueness rule and value
  semantics; both new columns are nullable with no default; `products.items.create` stays strict; the update
  schema only widens. Existing routes, event IDs, ACL feature IDs and widget spots are untouched; all new IDs
  are additive.

## User Journeys

### Journey J-PC-001 — A new supplier product gets a regular code

1. Buyer opens 供应商产品库 → 新建产品; the supplier select is required, 品牌 pre-fills from the supplier's 默认品牌.
2. Buyer picks 类别 (猫砂) and clicks 生成 beside 商品 SKU.
3. The system issues `PK-CL007` into the ledger and returns the breakdown, which renders under the field:
   `品牌 PK（PetKit）· 类别 CL（猫砂）· 序列 007`.
4. Buyer saves; the row stores `PK-CL007`; promoting it later writes that code into `products_products.sku`.
5. Failure: the supplier has no 默认品牌 and no 品牌 was chosen → the button is disabled with a localized hint
   naming the missing input; a ledger retry exhaustion returns 409 and the form offers 重新生成 without losing input.

### Journey J-PC-002 — An operator reads a code they did not generate

1. Operator opens a supplier product row created from a PetKit quotation (`P4108-UVC`).
2. The form shows the code with the badge 「沿用旧码」 and, underneath, what the parser could establish —
   `未匹配任何规则：沿用旧码（PetKit 旧编码，不重编）`; no 生成 button until 改用规范编码 is clicked.
3. Clicking 改用规范编码 asks for 类别, generates a new code, records `P4108-UVC` in the alias table and keeps
   the printed documents untouched.
4. Failure: the row is already promoted → the action is disabled with the reason (the master SKU must not
   diverge from the library row).

### Journey J-PC-003 — Business staff maintain the vocabulary

1. Staff opens 字典库, selects their organization, opens `product_brand`.
2. They add `PK — PetKit`; a code generated afterwards uses the `PK` prefix.
3. They try to rename the value `SP` to `SU` after codes exist → the write is refused with
   `dictionary_value_in_use`, while renaming the *label* (Super pawers → Super Pawers) succeeds and every
   breakdown picks the new label up immediately.

### Journey J-PC-004 — Legacy product stays editable

1. Staff opens a product whose SKU is a PetKit legacy code containing a character the SKU pattern forbids.
2. They edit its name and prices; the form submits the unchanged SKU.
3. The update succeeds (no charset re-validation of an unchanged SKU) and the audit entry records the change.
4. Failure: they *change* the SKU to another illegal string → 422 naming the allowed charset.

### Journey J-PC-005 — Second source for the same item

1. Buyer creates a library row for a second supplier for an item whose master product already exists and is
   already linked from the first supplier's row.
2. They click 建商品档案 → refused: the master is owned by another supplier product row.
3. They use 关联已有商品 instead; the master keeps the first supplier's data and the second row points at it.

## Data Models

### `ProductCodeRule` (`product_codes_rules`)

| Field | Type / nullability | Scope / index | Sensitive / encrypted | Lifecycle and validation |
|---|---|---|---|---|
| `id` | UUID, required | primary key | no | immutable |
| `tenant_id` / `organization_id` | UUID, required | composite scope index | no | trusted context only |
| `name` | text, required | unique per (tenant, org) including soft-deleted | no | 1–120 chars, trimmed |
| `mode` | text, required, default `generate` | — | no | `generate` \| `carry_over` |
| `segments` | jsonb, required | — | no | ordered array; exactly one `serial` segment; each `dictionary` segment names a dictionary key, a width and `join`. `join: true` glues a segment to the previous one with **no** separator — the business's own `SP-CL001` (not `SP-CL-001`) is brand + `-` + category+serial, which is why the separator belongs to the segment boundary rather than to the rule as a whole |
| `separator` | text, required, default `-` | — | no | `-` \| `_` \| empty |
| `serial_length` | integer, required, default 3 | — | no | 1–8 |
| `serial_scope` | text, required, default `brand_category` | — | no | `brand_category` \| `brand` \| `global` |
| `enforce` | text, required, default `warn` | — | no | `warn` \| `strict` |
| `is_active` | boolean, required, default true | — | no | inactive rules are not offered to the form and are skipped by parse |
| `created_at` / `updated_at` | timestamptz, required | `updated_at` is the optimistic-lock version | no | updated on every edit |
| `deleted_at` | timestamptz, nullable | — | no | soft delete; the name stays owned |

Rule validation (on create and update): every segment is either `dictionary` (with a known dictionary key and
length 1–8) or `serial`; exactly one serial; the worst-case rendering — dictionary values are bounded by their
declared length, the serial by `serial_length` — is ≤ 64 characters and matches `^[A-Za-z0-9._\-/]{1,64}$`
using the longest value currently in each dictionary. A rule that can emit a space, a Chinese character or a
`#` is rejected at save time, not at generation time.

### `ProductCodeLedgerEntry` (`product_codes_ledger_entries`) — append-only

| Field | Type / nullability | Scope / index | Sensitive / encrypted | Lifecycle and validation |
|---|---|---|---|---|
| `id` | UUID, required | primary key | no | immutable |
| `tenant_id` / `organization_id` | UUID, required | composite scope index | no | trusted context only |
| `rule_id` | UUID, required | index with the scope tuple | no | scalar id into `product_codes_rules` (no ORM relation) |
| `code` | text, required | **unique per (tenant, org)** — the issuance guarantee | no | written once; never updated |
| `brand_value` | text, required | part of the scope index | no | the dictionary value used |
| `category_value` | text, nullable | part of the scope index | no | null when the rule has no category segment |
| `serial` | integer, required | part of the scope index | no | monotonic within its scope; never reused |
| `created_at` | timestamptz, required | — | no | set on insert |

Append-only by contract: no `updated_at`, no `deleted_at`, no update or delete command, and no undo path.
Deleting a library row therefore cannot free its serial. Orphan entries (issued but never saved) are expected
and are surfaced as gaps in the sequence panel.

## Security, Privacy, and Compliance

- **Authorization:** every new route is gated by a concrete feature ID; no role-name checks. Generation is its
  own feature (`product_codes.codes.generate`) so a buyer can generate without being able to edit rules.
- **Tenant isolation:** rules, ledger and aliases carry `tenant_id` + `organization_id` and are filtered on
  both in every read and write; scope comes from the command context only. Cross-organization reads are
  impossible by construction (no endpoint accepts an organization id).
- **Sensitive data:** none. Brand/category values, codes and aliases are business identifiers; no PII, no
  credentials, no free text about people. `note` on an alias is operator-written internal text and is not
  printed on documents.
- **Abuse and failure modes:** issuance is bounded by retry count and rejects a rule that could emit illegal
  characters; alias creation validates the target exists and is live inside the writing transaction (the
  pattern already used by `purchasing/lib/supplierProductLinking.ts`); parse is read-only and rate-limited by
  the platform default; a code is never accepted from the client as authoritative — the ledger decides.

## Implementation Phases

### Phase 1 — 兼容性修复（不依赖新模块）

- **Deliverables:** `products/data/validators.ts` (widen `productUpdateSchema.sku` — the pattern leaves the

## Rollout, Migration, and Rollback

**Migration boundary.** Two additive migrations are generated by `yarn db:generate` and reviewed before
application (user approval required — never migrate to validate): one creates the three `product_codes_*`
tables and their indexes, the other adds `brand_value` to `purchasing_suppliers` and
`purchasing_supplier_products`. Neither touches existing rows: **no backfill, no data rewrite, no legacy code
is renamed**. Seeding is idempotent (`setup.ts` seeds dictionaries and the initial rule only when absent).

**Rollout order.** Phase 1 (compatibility fixes, no new module) → Phase 2 (module enabled, no consumer yet) →
Phase 3 (purchasing starts generating) → Phase 4 (legacy aliases). The generator is opt-in per row: nothing changes for a row until an operator clicks 生成.

**Migration & Backward Compatibility** (per `.ai/guides/upstream/BACKWARD_COMPATIBILITY.md`):

- Contract surfaces changed: `data/validators.ts` in `products` (the update schema **widens** — `sku` loses the
  charset pattern on the update path while the create path and the command's changed-value branch keep it),
  `purchasing` request/response schemas (**additive** optional `brandValue`), and new routes/features/events
  (**additive only**). No surface is removed, renamed or narrowed, so the deprecation protocol's steps 1–3 do
  not apply and no `UPGRADE_NOTES.md` entry is required.
- Stored data: unchanged. Existing `supplier_sku`, `item_no` and `products_products.sku` values keep their
  meaning; only their **labels** change (REQ-PC-011), which is not a contract surface.
- Downstream modules: `sourcing` (quote import) and `cross_border` (allocations) read the same columns and
  snapshots they read today; the promotion guard adds a new refusal for a case that previously overwrote data.
- Event IDs, ACL feature IDs, DI names, spot IDs and generated-registry exports are untouched; every new ID is
  additive.

**Rollback.** Remove the `enabledModules.push({ id: 'product_codes', … })` entry and run `yarn generate`: the
routes and pages disappear, `purchasing` keeps working with hand-typed codes (the 生成 button and the breakdown
simply vanish with their endpoints), and the three tables stay behind as harmless history — the ledger is the
only record of what was issued, and it must not be dropped if codes were issued. The label renames revert with
the locale files; the two nullable columns can stay (unused) or be dropped in a follow-up migration.

## Risks and Tradeoffs

| Risk / tradeoff | Impact | Mitigation / detection | Residual risk |
|---|---|---|---|
| A generated number is burned when the row is never saved | Gaps in the sequence | Documented; the sequence panel shows issued vs. used; the gap is cosmetic | Accepted — gaps are cheaper than a code that changes at save time |
| Concurrent issuance for the same brand+category | Two codes could collide | Unique index on the ledger + bounded retry; TEST-PC-002 exercises the concurrent path | Retry exhaustion is a 409 the operator resolves by regenerating |
| A rule is edited after codes exist | Older codes may parse as `partial` instead of `full` | Parse never fails; the breakdown shows unknown segments as-is; rule edits are audited and the ledger keeps the issuing `rule_id` | Accepted — codes are immutable, only their explanation can degrade |
| A code-list value is renamed | Every code using it would change meaning | Mutation guard refuses value changes and deletes once the ledger holds the value (REQ-PC-001, TEST-PC-005) | A value never issued can still be edited — intended |
| Grandfathering widens the update validator | A caller could keep an illegal SKU forever | The check still runs whenever the SKU **changes**; create stays strict; TEST-PC-007 covers both directions | Accepted — the alternative makes legacy rows uneditable |
| The promotion guard refuses a previously-allowed update | A workflow that relied on the silent overwrite now stops | The error names 关联已有商品, which achieves the same intent without data loss | Operators must learn the new action; the message is explicit |
| Alias search adds a subquery to two list routes | Slower list reads | Alias counts are small and indexed; the union is a `WHERE … OR id IN (…)` on an indexed column | Accepted; revisit only if a list route shows measurable regression |
| Legacy codes cannot be renumbered by design | The library keeps two code dialects | That is the requirement: documents are frozen, and re-coding is a per-row decision with an alias | Accepted — recorded in REQ-PC-008 |
| A migration on a table renamed across a module boundary runs too early on a fresh database | The ephemeral/CI database cannot initialize at all (observed 2026-09-24 with another session's `purchasing` migration on `purchasing_supplier_products`) | Place such migrations in a module registered after the renaming one and prove them with `yarn mercato test:integration` (empty database), not on the migrated dev database — `.ai/lessons/cross-module-rename-migration-ordering.md` | Accepted for migrations already committed in the wrong place; the trap recurs for every future migration on those tables |
